# 運作原理

這份文件說明 Threads Monitor 怎麼在**不登入、不用任何帳號或權杖**的情況下，取得一篇公開 Threads 貼文的數字，以及排程、狀態與資料的處理原則。文中的貼文代碼與帳號一律是假值（例如 `DFakeP0st01`、`example_user`）。

**兩個版本共用同一套規則**：資料夾版（`standalone/`）與網頁版的抓取方式、頁面解析、網址與分享連結還原、抓取頻率、狀態判斷與「NULL 不當 0」原則都相同。差別只在資料存放與介面：網頁版存在資料庫、有多帳號（[§12](#12-帳號與資料範圍)）；資料夾版存在同一個資料夾的 CSV。兩個版本都可以把貼文分組：網頁版的分組存在資料庫、每個帳號各自一套（沒有分組的貼文列在「未分類」）；資料夾版的分組就是資料夾（由 `urls.txt` 裡的 `## 標題` 行決定，沒有分組的貼文放進名為「未分組」的資料夾；系統語言不是中文時，這個資料夾叫 `Ungrouped`）。文中提到的檔名與設定鍵（`app/…`、`config/threads.php`、`THREADS_*`）是網頁版的實作位置。

> 以下內容是 2026 年 10 月實測時的狀況。Threads 的網頁是 Meta 的內部格式，沒有任何相容性保證，隨時可能改變。

## 1. 一句話說明

用 Googlebot 的 User-Agent 對貼文的公開網址發一次普通的 HTTP GET，伺服器會回一份「伺服器端渲染（SSR）」的 HTML，裡面內嵌了這篇貼文的 JSON 資料；從那段 JSON 讀出讚數、留言、轉發、引用、分享、發布時間與貼文內文，從頁面另一段設定讀出觀看數。排程依照發文後經過的時間決定多久抓一次，72 小時整抓最後一次，那一次的數字就是「72 小時最終數字」。

## 2. 為什麼不用官方 API

官方 Threads API 的 insights 端點**只能讀授權者自己的貼文**。對別人的貼文：

- 沒有任何官方端點能把貼文網址或代碼換成 API 用的 media id。
- oEmbed 只回嵌入用的 HTML，沒有數字也沒有 id。
- 關鍵字搜尋、個人頁探索之類的端點可以列出別人的公開貼文，但不含任何指標。

所以「任意公開貼文的數字」沒有官方路線，本專案改走未登入的公開頁面。代價見 [§11](#11-已知風險)。

## 3. 抓取方式：User-Agent 決定拿到什麼

同一個貼文網址，用不同 User-Agent 請求，伺服器回的內容完全不同（實測全部 HTTP 200）：

| User-Agent | 回應大小（約） | `og:description` | 貼文 JSON（含數字） | 觀看數設定 |
|---|---|---|---|---|
| 一般桌機瀏覽器 | 280 KB | 無 | 無（只有骨架，要靠瀏覽器執行 JS） | 無 |
| 行動版瀏覽器 | 590 KB | 有 | 無 | 有 |
| `facebookexternalhit/1.1` | 570 KB | 有 | 無 | 有 |
| **Googlebot** | 660–700 KB | 有 | **有** | 有 |

- 純 HTTP 只有 Googlebot UA 拿得到完整數字，所以預設的 `THREADS_USER_AGENT` 是 Googlebot 的字串（`config/threads.php`）。
- 一次請求約 660–700 KB，不需要開瀏覽器。
- 不帶 cookie、不帶任何權杖、不登入。
- 用無頭瀏覽器（headless Chromium）未登入開啟頁面，也拿得到同一份 JSON；這是 Googlebot 路線被封時可以考慮的備援，目前**尚未實作**。
- 每次抓取之間預設間隔 3 秒（`THREADS_POLITENESS_SLEEP_MS`），單次逾時 30 秒（`THREADS_TIMEOUT`）。

抓取結果的分類（`app/Threads/PublicPageFetcher.php`）：

| 狀況 | 分類 |
|---|---|
| HTTP 200，找得到貼文 JSON | 成功 |
| HTTP 404 / 410 | `gone`（貼文已刪除或不公開） |
| HTTP 429，或 200 但既沒有貼文 JSON 也沒有 `og:description` | `blocked`（被限流、登入牆或驗證頁） |
| HTTP 200，有 `og:description`，但找不到貼文 JSON | `parse_failed`（頁面格式可能改了） |
| 連線失敗 | `network_error` |
| 其他 HTTP 狀態 | `http_error` |

另外有一條**未經實測**的推測規則：頁面有 `og:description`、但 `og:url` 不再指向這篇貼文時，視為已刪除（`gone`）。其他判斷不出來的情況一律歸 `parse_failed`，寧可顯示失敗，也不要把「解析壞掉」誤標成「貼文刪除」。

## 4. 資料在頁面的哪裡：每個欄位的來源

貼文資料放在頁面裡的 `<script type="application/json">` 區塊，是 Meta 前端框架（Relay）預先載入的資料。這些區塊很多、巢狀很深，中間的陣列索引每次部署都可能不同，所以程式**不寫死路徑**，而是：

1. 只解析內容包含 `"<貼文代碼>"` 字串的區塊（省時間）。
2. 遞迴往下找，第一個同時滿足「`code` 等於貼文代碼」且「有 `taken_at` 鍵」的物件，就是這篇貼文（`media`）。最多往下 64 層。

找到 `media` 之後，欄位對應如下（`tpai` 指 `media.text_post_app_info`）：

| 指標 | 來源 | 備註 |
|---|---|---|
| 讚 likes | `media.like_count` | |
| 留言 replies | `tpai.direct_reply_count` | 只算直接回覆 |
| 轉發 reposts | `tpai.repost_count` | |
| 引用 quotes | `tpai.quote_count` | |
| 分享 shares | `tpai.reshare_count` | 舊貼文、串內回覆常常是 `null`，**存 NULL，不存 0** |
| 發布時間 | `media.taken_at` | Unix 秒，UTC |
| 觀看 views | 頁面設定 `BarcelonaLoggedOutExpansionGating` 裡的 `view_counts` | 不在 `media` 物件裡，見 [§5](#5-觀看數views的性質) |
| 作者帳號 | `media.user.username` | 第一次抓取成功之前，網頁版顯示的是你加入的網址裡的帳號名稱，並標示「**未驗證**」（任何人都能在網址裡打任意的 `@名稱`）；第一次抓取成功後才會確認或更正。「開啟貼文」連結一律使用 `https://www.threads.com/t/<代碼>` |
| 數字 id | `media.pk` | 不是官方 API 的 media id |
| 作者隱藏數字 | `media.like_and_view_counts_disabled` | 為 `true` 時讚數與觀看數一律記為 NULL，畫面標示「作者隱藏數字」。留言、轉發、引用、分享不受影響 |
| 貼文內文 | `media.caption.text` | 只在第一次抓到內文時存一次，之後貼文被編輯不會跟著更新。沒有內文 → NULL |

觀看數用的正規表示式：

```
"BarcelonaLoggedOutExpansionGating",\[\],\{[^{}]*?"view_counts":(\d+)
```

數值只接受非負整數；負數、非數字、超過 18 位數一律當成拿不到（NULL）。

## 5. 觀看數（views）的性質

- 它是**網頁上顯示的觀看數**：桌機版網頁頁首會顯示「X 次瀏覽」，實測 6 篇樣本，`view_counts` 和畫面上的數字全部相符（畫面是縮寫，例如「1.3 萬」）。
- 支持它是「這一篇」觀看數的其他證據：每篇貼文的值都不同；同一篇在不同 UA 下的值完全相同；只出現在單篇貼文頁；讚數 ÷ 觀看數大約 0.6%～1.3%；數字會隨時間增加。
- 它**有延遲**：實測間隔兩分鐘的兩次抓取，讚數增加了、觀看數沒變，推測有幾分鐘的快取。
- 它**不保證等於**作者在 App 或官方 API 看到的觀看數，這點沒有驗證過。
- 它放在一段「未登入時的介面設定」裡，旁邊還有 `"enable_view_counts": false`。這是所有欄位裡**最可能被改版拿掉**的一個；拿不到時程式存 NULL，絕不補 0。

## 6. 網址解析與分享連結還原

### 6.1 接受的網址

所有格式都正規化成同一個 **貼文代碼（shortcode）**，它是資料庫裡的唯一鍵：同一篇貼文換網域、換格式、帶不同參數，都算同一筆。

```
https://www.threads.com/@example_user/post/DFakeP0st01
https://www.threads.net/@example_user/post/DFakeP0st01
https://threads.com/t/DFakeP0st01
```

可以帶 `?igshid=…` 等參數，也可以有結尾斜線。

- `threads.net` 會 301 轉到 `threads.com`；程式一律用 `threads.com` 的標準網址抓取。
- 貼文代碼的字元集是 `A-Z a-z 0-9 - _`。
- 不符合格式的網址在輸入時就擋下，不會建立一筆永遠抓不到的資料。

### 6.2 分享連結

在 Threads App 按「分享 → 複製連結」，有時得到的是這種網址：

```
https://www.threads.com/share/<share-code>/
```

這裡的分享代碼**不是**貼文代碼，看不出是哪一篇。還原方式：

1. 用 Googlebot UA 對分享連結發一次 GET，**不自動跟隨轉址**。
2. 伺服器回 HTTP 302，`Location` 標頭就是原本的貼文網址（通常會帶一個 `xmt` 追蹤參數）。
3. 從 `Location` 解析出貼文代碼，之後照一般貼文處理。

資料庫只存還原後的**乾淨網址**（`https://www.threads.com/@帳號/post/代碼`）。分享代碼與 `xmt` 參數是分享者的追蹤資訊，**一律不存**。

## 7. Shortcode 解碼：從代碼算出時間

Threads 沿用 Instagram 的 id 體系，貼文代碼可以不連網直接解出數字 id 和一個時間：

1. 字母表（URL-safe base64）：`ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_`
2. `pk = Σ index(c) × 64^k`，最左邊的字元是最高位。
3. `created_ms = (pk >> 23) + 1314220021721`（Instagram 的 epoch，毫秒）。

範例（假代碼，只示範計算）：`DFakeP0st01` → `pk = 3556315264011394357` → `2025-01-29 15:50:37.762 UTC`。

注意事項：

- `pk` 約 4×10¹⁸，接近 64 位元整數上限，程式用 PHP 的 bcmath 以字串計算（所以需要 bcmath 擴充）。
- 實測 8 篇真實貼文：解出的 `pk` 和頁面上的 `media.pk` **逐位相同**。
- 但解出的是 **id 建立時間**，不一定等於發布時間 `taken_at`：7 篇誤差在 +1 秒內，1 篇比 `taken_at` 早 8.6 秒。排程發文（先寫好、晚點才發）可能差更多，沒有驗證過。
- 所以 `published_at` **以頁面的 `taken_at` 為主**；解碼只在還沒抓到頁面時當暫時的估計值，並標記來源為 `shortcode_decode`，畫面會標示「推算」。第一次成功抓到頁面後就改用 `taken_at`。
- 這個 `pk` 不是官方 Graph API 的 media id，不能拿去呼叫官方 API。

## 8. 抓取頻率

排程以**發布時間**為起點（不是加入追蹤的時間），預設值（`config/threads.php` 的 `poll_bands`；資料夾版是 `PollPlanner.DefaultBands`）如下：

| 發文後 | 頻率 |
|---|---|
| 0–72 小時 | 每 60 分鐘 |
| 72 小時整 | 最後一次，寫入最終數字 |

- 抓取時間點落在以各區段起點為基準的固定網格上，排程晚跑幾分鐘也不會讓之後的時間點一路漂移；最後一個點一定是「發布時間 + 72 小時」。
- 系統排程每 5 分鐘執行一次 `threads:poll-due`，挑出「下次抓取時間 ≤ 現在」的貼文，一篇一篇抓（每次最多 60 篇，每篇之間間隔 3 秒）。一篇失敗不會影響其他篇。
- 預設一篇貼文大約抓 72＋1 次（加入時抓第一次，之後每小時一次）。未登入抓取被擋的風險隨請求量增加，所以排程可以設定：`.env` 的 `THREADS_POLL_BANDS`（資料夾版是 `settings.ini` 的 `poll_bands`），格式是用逗號分隔的「`起-迄:分鐘`」區段。例如 `0-24:60,24-72:180` 就是改回前 24 小時每小時一次、之後每 3 小時一次（大約 24＋16＋1 次）。
- 這個值的規則：時數是 0 以上的整數、每段的迄大於起、各段依序排列且不重疊（段與段之間可以留空檔）、間隔至少 5 分鐘。任何一段不合法時整個設定都不採用，改用預設值（網頁版在 Laravel log 寫一筆警告；資料夾版寫進 `log.txt`）。已經在追蹤中的貼文，下一次抓取完成後就依新的排程安排，不需要轉移資料。
- **沒有被區段涵蓋的時間不抓。** 發文後經過的時間落在兩段之間的空檔時，下一次抓取是下一個區段的起點；第一個區段的起點大於 0 時，在它之前除了加入時的第一次抓取之外都不抓；最後一個區段結束後，下一次就直接是追蹤結束時的最後一抓。例如 `0-24:60,48-72:60`：第 1 到第 24 小時每小時抓一次、第 48 到第 72 小時每小時抓一次，第 24 到第 48 小時之間不抓。
- 每天 04:10（Asia/Taipei）執行 `threads:prune-raw`，把 7 天前快照的除錯欄位清空，只留數字。
- 72 小時可以用 `THREADS_TRACK_HOURS` 調整，但上面的抓取區段只涵蓋 0–72 小時：設得比 72 大時，第 72 小時到結束之間除了最後一次抓取不會再抓；設得比 72 小的時候，追蹤就會提早結束。頁面上的標示（例如「72 小時最終」）會跟著這個值變。

## 9. 狀態機

| 狀態 | 意思 |
|---|---|
| `pending` | 剛加入，等待第一次抓取 |
| `tracking` | 追蹤中 |
| `done` | 已完成，最終數字已寫入 |
| `gone` | 貼文已刪除或不公開，停止追蹤，保留已有的快照 |
| `failed` | 失敗，停止追蹤，畫面顯示原因 |

轉換規則（`app/Threads/PostPoller.php`）：

- **成功**：寫一筆快照；若已到 72 小時，這一筆就是最終數字，轉 `done`；否則轉 `tracking`，算下一次抓取時間。
- **加入時已超過 72 小時**：貼文進入系統（第一次被任何人加入）的時間已經在發布時間 + 72 小時或之後時，只抓一次就寫成最終數字，並標記「加入時已超過 72 小時，非 72 小時那一刻的數字」。別人已經在追蹤的貼文，再有人加入也不會改變這個標記。
- **`gone`**：停止追蹤；最終數字用最後一筆成功的快照，時間記成那一筆的實際時間。只要成功抓過至少一次，清單與貼文頁就會把這些數字標成「刪除前最後數字」顯示。
- **其他失敗**（`blocked`、`parse_failed`、`network_error`、`http_error`、程式例外）：失敗次數加一，15 分鐘後重試（不超過 72 小時的截止點）。
  - 連續失敗 5 次（`THREADS_MAX_CONSECUTIVE_FAILURES`）→ `failed`；之前只要有成功抓過，那一筆的數字會保留下來，標成「失敗前最後數字」顯示。
  - 第 72 小時那一次失敗 → 用最後一筆成功的快照當最終數字，`final_captured_at` 記成**那一筆的實際時間**，不假裝是 72 小時整；完全沒有成功過 → `failed`。
- **失敗必須看得見**：最後一次錯誤的分類與訊息存在 `last_error`，貼文頁會顯示，並註明連續失敗幾次。
- 任何一次抓取都不會讓整個排程中斷：例外會被記成這篇貼文的失敗。

## 10. NULL 不當 0

這是整個專案最重要的資料原則：

- **NULL＝拿不到**（欄位不存在、作者隱藏、頁面改版），**0＝真的是零**。兩者在畫面上顯示也不同：「無法取得」（英文介面是 Not available）vs.「0」。
- 快照與最終數字的每個指標欄位都是 nullable，抓到什麼就原樣存什麼，不補值、不沿用上一次的值。
- 圖表不畫 NULL 的點。
- 這樣做的原因：如果把拿不到當 0，改版當天所有貼文的觀看數會「掉到 0」，看起來像真實資料，誰也發現不了。

## 11. 已知風險

1. **Googlebot UA 從非 Google 的 IP 發出**：只要 Meta 開始驗證反向 DNS（確認來源真的是 `googlebot.com`），所有抓取都會變成 `blocked`。專案公開之後被針對的機率更高。備援（無頭瀏覽器）尚未實作。
2. **頁面格式是內部格式**：遞迴尋找貼文物件撐得過小改版，撐不過大改版。改版時會出現大量 `parse_failed`。
3. **觀看數最脆弱**：見 [§5](#5-觀看數views的性質)，而且不保證等於官方數字。
4. **限流門檻沒有壓測**：實測時單一 IP 約 50 次請求全部成功，這個量不能推論長期排程的情況。追蹤量放大前請先觀察 `blocked` 的比例。
5. **「貼文已刪除」的判斷有一部分是推測**：見 [§3](#3-抓取方式user-agent-決定拿到什麼) 最後一段。
6. **服務條款**：未登入抓取公開頁面可能違反 Meta 的服務條款，IP 也可能被封。是否使用、如何使用由你自行判斷並承擔責任。

## 12. 帳號與資料範圍

本節只適用於網頁版。

- 不開放註冊。第一個管理員用指令建立（`php artisan threads:create-admin <email>`，或安裝程式 `threads:install` 時建立）；其他帳號由管理員在 `/users` 建立、編輯、重設密碼、停用或刪除。
- 每個人可以在 `/account/password` 改自己的密碼（至少 12 個字元）。改自己的密碼會登出自己的其他登入；管理員重設某人的密碼或停用帳號時，該帳號的所有登入都會結束。已登入的帳號被停用後，下一個請求就會被登出。
- 登入次數限制：同一個 email 每 10 分鐘 10 次、同一個 IP 每分鐘 5 次（IPv6 以 /64 計）。同一個 email 的不同寫法（大小寫、重音符號、全形字母、空白）算在同一個額度裡。不存在的 email、被停用的帳號、密碼錯誤，顯示的訊息都一樣，回應時間也和帳號存不存在無關：三種情況都剛好做一次密碼雜湊比對。
- **清單各自獨立，抓取資料共用**：同一篇貼文在系統裡只有一筆、只抓一次；第二個人加入同一篇時，只是把它掛到自己的清單，不會重新抓取或重置狀態。他看得到這篇貼文的全部快照，包括他加入之前抓到的。
- 加入或移除貼文後顯示的訊息，不論其他帳號有沒有在追蹤都一樣，所以無法從訊息看出別人追蹤了什麼。
- 標籤與備註是每個人對自己清單裡每篇貼文各自存的（存在清單項目上，不在共用的貼文上），其他帳號看不到。
- 「從我的清單移除」只影響自己；最後一個人移除時，這篇貼文和它的快照才會被刪除、停止追蹤。
- 管理員也看不到別人的清單，帳號管理頁只顯示每個人追蹤了幾篇。
- 系統永遠至少保留一位啟用中的管理員；忘記密碼時，在主機上重跑 `threads:create-admin <同一個 email>` 就能重設，並恢復管理員與啟用狀態。

## 13. 分時紀錄、分組、標籤與搜尋

本節只適用於網頁版（`app/Threads/SnapshotDeltas.php`、`app/Http/Controllers/TrackedPostController.php`）。

**分時紀錄。** 貼文頁列出每一筆快照（六個數字都有）；清單上的每篇貼文也有可以展開的同一份分時紀錄（觀看、留言、轉發、分享）。每個數字下方是和前一筆相比的增量：

- 只有前後兩筆都有數字時才計算增量；任一筆是 NULL，增量就顯示為無法計算，不會當成從 0 跳上來或掉到 0。
- 增量另外換算成每小時增量，但**只在兩筆相隔至少 0.5 小時時**才換算。失敗後的重試可能只隔幾分鐘，用這麼短的間隔去除會算出沒有意義的尖峰。
- 貼文頁還會顯示兩筆之間相隔幾小時。

**分組、標籤與備註**和清單本身一樣，屬於每個帳號自己：其他帳號看不到。

- **新增貼文只需要貼網址。** 分組、標籤、備註都是建立之後再設定：清單上每張卡片都有「編輯」，可以直接改這三樣；貼文詳細頁頂端也有同樣的編輯區。
- **分組**：一篇貼文在一個帳號底下最多屬於一個分組。清單依分組分區顯示，每個分組是可以點開的區塊，標題顯示分組名稱和篇數。分組區塊預設收合；有篩選時，有符合結果的區塊會自動展開，沒有篩選時瀏覽器會記住你展開了哪些區塊（只存在那個瀏覽器裡）。沒有分組的貼文放在最後的「未分類」。清單上方的「管理分組」可以新增、改名、刪除、調整順序。刪除分組時，裡面的貼文回到「未分類」，貼文和資料都不受影響。分組名稱最多 40 字，每個帳號最多 100 個分組；只差在大小寫、重音符號或全形字母的兩個名稱視為同一個名稱。
- **標籤**：用逗號分隔；每篇最多 20 個，每個最多 30 字，不能包含逗號或 `#`；開頭的 `#` 會被去掉；比對時不分大小寫，也不分重音符號與全形、半形（`Café`、`cafe`、`ＣＡＦＥ` 是同一個標籤）。儲存標籤會整組取代這篇貼文原本的標籤；沒有任何貼文在用的標籤會自動消失。
- **備註**：每篇一則，最多 1000 字。

**搜尋與篩選。** 清單可以用網址參數篩選，所以篩選結果可以加入書籤。結果仍然依分組分區顯示；沒有符合結果的分組不顯示。

| 參數 | 意思 |
|---|---|
| `q` | 關鍵字（最多 100 字），搜尋作者帳號、貼文代碼、貼文內文、你的備註、你的標籤名稱，以及這篇貼文所在的你的分組名稱。不分大小寫，英文以外的字母（例如 `É`／`é`、希臘字母）也一樣，SQLite 與 MySQL 都是 |
| `status` | `pending`、`tracking`、`done`、`gone`、`failed` 其中之一 |
| `tag[]` | 你的一個標籤；要多個就重複這個參數（最多 20 個）。貼文必須**全部**符合 |
| `group` | 你的一個分組的 id，或用 `none` 代表「未分類」 |

例如：`/?q=launch&status=done&tag[]=campaign`。不合法的值會被忽略，不會出錯；你沒有的標籤會得到空清單。搜尋與篩選永遠只看你自己的清單。
